# 문제 2 - 재고 API 자동화 테스트

로컬 스텁 서버에 실제 HTTP 요청을 보내는 **18개 TC, 기본 25개 실행 케이스**입니다. 실제 B마트 서버에는 접속하지 않습니다.

## 실행 방법

Windows에서 이 폴더의 배치 파일을 더블클릭합니다.

- **[run_tests.bat](run_tests.bat):** 기본 API 시험 25개 실행
- **[run_concurrency.bat](run_concurrency.bat):** 무작위 동시 주문 50회 실행

Python 3.11 이상을 확인하고, 가상환경과 라이브러리를 준비한 뒤 실행합니다. Python이 없으면 winget으로 설치하며, winget이 없으면 Python을 직접 설치해야 합니다. 최초 환경 구성에는 인터넷이 필요합니다. 저장소 루트의 `tools/` 폴더도 필요하므로 전체 저장소를 함께 내려받으세요. 스텁 서버는 테스트가 자동으로 시작하고 종료합니다.

반복 횟수 변경 또는 같은 무작위 조건 재현:

```bat
run_concurrency.bat -Runs 100
run_concurrency.bat -Seed 2992690177
```

같은 시드, 반복 횟수와 간격 범위를 지정하면 고객 순서와 설정 간격을 동일하게 재현할 수 있습니다. 실제 측정 시간은 실행마다 달라질 수 있습니다.

배치 없이 실행하려면 문제2 폴더에서 다음 명령을 사용합니다.

```powershell
python -m venv .venv
.venv\Scripts\python.exe -m pip install -r requirements.txt
.venv\Scripts\python.exe -m pytest -v
```

## TC와 결과 확인

- [전체 TC 명세서](docs/B마트_재고_API_TestCase_무작위반복.xlsx)
- [기본 시험 결과: 25개 통과](reports/runs/20261006-202015-127/시험성적서.html)
- [동시 주문 결과: 50회 통과](reports/runs/20261006-201956-677/시험성적서.html)

TC는 18개입니다. 잘못된 수량 6종과 동시 주문 3회를 포함하면 기본 실행은 25건입니다. 동시 주문 TC-CON-001은 별도로 50회 반복한 기록을 첨부했습니다.

실행이 끝나면 시험성적서가 브라우저에서 열립니다. 성적서, CSV, JSON, JUnit과 로그는 `reports/runs/실행시각/`에 저장됩니다. 동시 주문은 시작 시각, 전송과 접수 순서, 간격, 성공한 고객과 품절된 고객도 기록합니다. Excel에는 저장 당시 결과를 넣었으며 실행 시 자동 갱신되지는 않습니다.

## 구조 설계

- **[app.py](app.py) - 스텁 서버:** 메모리에 재고와 주문을 저장합니다. 재고 확인, 차감, 주문 저장을 같은 잠금으로 보호하고 서버 접수 순서대로 처리합니다.
- **[conftest.py](conftest.py) - fixture와 데이터 준비:** 테스트마다 독립된 서버, 포트, 재고를 준비하고 실패해도 종료합니다. 기본 재고는 `P001=5`, `P002=8`이며 품절 시험은 `0`, 동시 주문은 `1`로 지정합니다.
- **[helpers.py](helpers.py) - 요청과 검증 헬퍼:** HTTP 호출 및 재고, 주문, 취소, 오류 검증을 공통화합니다. 기대값은 테스트가 직접 지정하며 서버 계산 로직을 재사용하지 않습니다. 주문 건수는 조회 API가 없어 읽기 전용 내부 주문 기록으로 보조 확인합니다.
- **[test_stock_api.py](test_stock_api.py) - 테스트 시나리오:** 준비한 데이터로 요청하고 결과를 판정합니다. TC ID를 Excel 및 [test_cases.json](docs/test_cases.json)과 연결합니다. 잘못된 수량 6종과 동시 주문 3회를 매개변수화해 18개 함수가 기본 25회 실행됩니다.

### 동시 주문

매 회차 재고를 1개로 초기화합니다. 먼저 요청할 고객(A/B)과 10~50ms 간격을 무작위로 선택합니다. 첫 요청이 서버에 접수된 시점부터 선택한 간격을 기다린 뒤 두 번째 요청을 보냅니다. 두 요청은 테스트용 동기화 지점에서 재고 처리 직전에 대기하고, 모두 접수되면 처리를 시작합니다. 성공과 품절은 실제 재고 처리 결과로 확인합니다.

선착순은 스텁 서버가 접수 번호를 부여한 순서로 정의합니다. 네트워크 패킷의 최초 도착 순서를 측정하는 것은 아닙니다.

**통과 조건:** 먼저 접수한 주문 1건 성공, 나머지 1건 품절, 최종 재고 0, 저장 주문 1건. 실측 서버 접수 간격은 설정값 이상 100ms 미만이어야 하며, 벗어나면 재시도 없이 실패로 기록합니다. 100ms는 시험 조건이며 서비스 응답 시간 기준은 아닙니다.

## API 가정

- `GET /v1/products/{productId}/stock`: 재고 수량과 품절/주문 가능 여부 반환(200), 재고 변경 없음
- `POST /v1/orders`: `productId`, `customerId`, 양의 정수 `quantity`를 받아 주문 확정 및 차감(201). 품절/재고 부족은 409, 잘못된 입력은 400, 없는 상품은 404이며 상태를 변경하지 않음
- `POST /v1/orders/{orderId}/cancel`: 취소 및 재고 복구(200). 반복 취소는 복구 수량 0, 없는 주문은 404

주문 생성은 결제가 승인된 요청으로 가정합니다. 실제 결제/환불, 인증, 관리자 수정, 앱 화면 갱신과 다중 서버 환경은 구현 범위에 포함하지 않았습니다.

## 요구사항 ID

TC 명세서의 SWRS-01~06은 과제의 요구사항을 구분하기 위해 직접 부여한 ID입니다. 실제 서비스의 내부 요구사항 ID가 아닙니다.
